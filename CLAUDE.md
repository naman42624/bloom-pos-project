## What this is

An internal operations app for a flower shop: multi-employee, multi-channel orders (WhatsApp, website, email, walk-in), in-house delivery. **It is live and in daily use at the counter** — this is not a greenfield project. Currently mid-redesign: fixing order flow, staff/employee identity, cash register, settlements, and attendance, which are inconsistent/broken in practice despite being previously marked "complete" (`PROGRESS.md` tracked 241/270 tasks across 10 phases before this redesign started).

## Stack — do not change without explicit user approval

- **Backend**: Express.js + JWT auth + PostgreSQL via `pg` (`server/`).
- **Frontend**: Expo (React Native) + React Navigation (not Expo Router). Targets iOS, Android, web from one codebase.
- Two reference docs were consulted for ideas: `/Users/gauravbhatia/Downloads/files/petal-prd.md` and `build-plan.md`. Their **concepts** are being adapted (unified order inbox, channel tag, buyer≠recipient, cost/margin separation, PIN quick-switch). Their **stack** (Supabase, Row-Level Security, Expo Router, TypeScript, NativeWind, offline-first sync) is explicitly NOT being adopted — this project stays on Express/JWT/pg. Don't suggest migrating to Supabase/RLS.

## Non-negotiable constraints

1. **Live production data — never lose it.** Every schema change is additive-only: new columns, new tables. Never `DROP`/`RENAME`/restructure a table or column already holding live data without an explicit, separately-approved migration plan with a backup taken first. Read the `db-migration-safety` skill before writing any migration touching `server/config/database.js` or any SQL migration file.
2. **Users are non-technical, first-time users of any business software.** Counter staff, florists, and riders have never used an app like this before. Every staff-facing flow must be obvious with zero training. Read the `staff-ux-checklist` skill before finalizing any staff-facing screen or flow design.
3. **No offline-first requirement.** Shop connectivity is reliable — don't build a local-write-queue/background-sync system; a simple retry/error message on a dropped request is sufficient.
4. **Customer self-ordering stays in scope.** Do not remove `CustomerShopScreen.js` or the `customer` role — the user explicitly chose to keep this, diverging from the reference PRD's staff-only stance.
5. **Approach is repair-in-place, not a rewrite.** Reuse working modules (inventory, products/QR, POS cart fundamentals) rather than rebuilding them. See the project memory file for the full decision log if more history is needed.

## Target role model (migrating to this from today's single generic "employee" role)

Owner · Manager · Sales/Counter Staff · Florist/Prep Staff · Delivery Rider · Customer.

- Manager: team-wide sales visibility; cost/margin data hidden by default (owner can toggle it on).
- Staff login: **employee code + PIN** on a shared counter device, fast identity switch, no OTP dependency. Owner/Manager keep phone + password on their own personal devices. (Today: no employee_code/PIN concept exists at all — everyone logs in with phone+password.)

## Locations

Single location today, expanding soon. Keep the data model multi-location-capable (it already is) but don't over-invest in multi-location UI polish yet.

## Order channels (real today, not aspirational)

WhatsApp, Website, Email, Walk-in/Phone. None need API integration — website orders are logged manually by staff exactly like WhatsApp/email. All four need a `channel` tag distinct from fulfillment type (`order_type`), which doesn't exist yet.

## UX design principles — every staff-facing screen, no exceptions

- Assume the person has never used a business app before in their life. No jargon, no hidden gestures, no multi-level menus for anything done daily.
- Big tap targets, large legible text, one clearly primary action per screen.
- The common-case path must be the *shortest* path. A plain counter sale target: well under 6 taps, well under 30 seconds.
- **Never cut functionality for the sake of simplicity.** Rare/advanced actions can live one level deeper (not deleted) — simple ≠ stripped-down.
- Prefer showing over asking: sensible defaults, pre-filled fields, remembered last choices (e.g. last channel used) over blank forms demanding input.
- Errors say what to do next in plain language ("Register isn't open — tap here to open it") never a technical message.
- See the `staff-ux-checklist` skill for the concrete pre-ship checklist to run any new/changed staff screen through.

## Known structural debt — don't be surprised by this, and don't "fix" it accidentally as a side effect of other work

- `server/config/schema.sql` is **dead** — never loaded at runtime, don't trust it as ground truth. The real live schema is assembled by `server/config/database.js`'s `ensureCoreTables()` plus **116 idempotent `ensureColumn()` patch calls** run on every server boot, which have silently added/renamed columns and dropped CHECK constraints over time.
- **The corollary that actually bit us (2026-09-10):** if a schema change is ever made directly against the local dev DB by hand — a manual `ALTER TABLE`, a dropped constraint, a psql session — and isn't *also* written as a patch in `database.js`, it silently only exists on dev. Production only ever gets schema changes from that file's patch list on boot, so dev and prod quietly diverge with no error until the missing piece is hit live. This caused two real prod crashes found the same session: `refunds.requested_by`/`approved_by` (added to dev by hand at some point, never patched in — every refund attempt in prod had 500'd since commit `c5b865e9`) and `users_role_check` (dropped on dev when `counter_staff`/`florist_staff` were added, never patched in — creating either role in prod 500'd). Both fixed (see sub-project 3's continuation note above). **Before assuming a route "already works" because it works locally, check whether the columns/constraints it depends on were ever actually codified in `database.js`** — dev's live schema is not proof of what production has.
- **Two DB access layers coexist**, sometimes in the same route file: `database.js`'s `getDb()` shells out to the `psql` binary via `spawnSync` **per query** (sync, subprocess per call — a likely real performance cost); `database-async.js`'s `getDb()` is a proper async `pg.Pool`. Prefer the async layer for any new/touched code; don't expand use of the sync one.
- A `customers` table exists in `database.js` but is **dead/unused** — `server/routes/customers.js` reads/writes `users` (role='customer') exclusively. Don't assume the `customers` table holds real data, and don't touch it without checking first — leave it alone unless a specific task calls for cleaning it up.
- ~~Cash-register-open enforcement exists only client-side~~ — **fixed** (sub-project 3, see roadmap item 3 above): now hard-enforced server-side at every known cash-write site via `server/utils/register-guard.js`. Not yet checked: the customer self-order endpoint and the recurring-order processor — worth a quick audit before considering sub-project 3 fully closed.
- Two parallel dashboards coexist: `DashboardScreen.js` and `DashboardScreenV2.js`, toggled by a settings flag. Old one (V1) not yet removed.
- `products.estimated_cost` is currently **not** role-filtered — visible to every authenticated role today, unlike `materials.avg_purchase_cost` which is correctly owner-only. This directly contradicts the "no sensitive data to employees" requirement and needs fixing (sub-project 8; sub-project 2 concluded without touching this).
- The 4 live `employee` accounts stay on `employee` until the owner manually promotes each to `counter_staff`/`florist_staff` via the existing role-change UI (`UserFormScreen.js`, no forced migration) — expect `employee` to coexist with the two new roles indefinitely, not a transitional state to "clean up."
- `useIdleLock`'s touch-based activity signal has two known coverage gaps, both opportunistic follow-ups, not blocking: (1) it only reaches React Native `Modal` content on `QuickCheckoutScreen.js` and `LogOrderScreen.js`'s voice-note modals — the same gap exists in principle across ~27 other screens using `Modal` (`grep -rl "<Modal" app/src/screens/*.js`); `bumpActivity` is exported from `app/src/hooks/useIdleLock.js`, wire via `onTouchStart={bumpActivity}` on the modal's outer content view. (2) Was found live to also miss ALL mouse-wheel/trackpad scrolling on web (no touch event fires) — fixed centrally, not per-screen, via `window.addEventListener('wheel'/'scroll', bump)` in `RootNavigator.js` (2026-09-01), so this one's actually closed for web; native scroll already worked (a touch-scroll starts with a real touch-down).
  - The lock architecture itself changed 2026-09-01: locking used to unmount `MainNavigator` entirely (swapped for `LockedNavigator`), wiping any in-progress screen state — a staff member lost a whole order draft to this. Now `MainNavigator` stays mounted and the lock screen renders as an overlay on top of it (`RootNavigator.js`), keyed by `user?.id` so a genuine staff switch (different PIN) still force-remounts clean, but the same person re-entering their own PIN keeps all state. Side effect: screens don't lose React Navigation focus during a lock anymore, so anything relying on `useFocusEffect` to refresh on return needs its own explicit `locked`-transition refetch — done for `DashboardScreen.js`, not yet audited elsewhere (same "opportunistic, not exhaustive" caveat as the two gaps above).
- **`database-async.js`'s `bindParams()` has a real footgun**: it toggles an "inside a string" flag on every `'` character with no awareness of `--` SQL comments, so a single stray apostrophe inside a hand-written comment (e.g. `-- today's fix`) silently desyncs every `?` placeholder for the rest of that query — 500ing the endpoint with no error until someone live-tests that exact code path. This actually happened (`GET /production/my-tasks` broke for every caller from one comment). Fixed both the trigger and the root cause — `bindParams()` now skips `--` line comments before scanning — but it still has **no equivalent handling for `/* */` block comments** (none exist in the codebase's SQL today, so untested); avoid introducing one, or extend the skip logic first if you do. Moral: never put an apostrophe in a SQL comment in this layer, full stop — the parser can't tell it from a real string boundary.
- `GET /api/users` is intentionally owner/manager-only — it's the full account directory (owner/manager/customer included), too broad to open to staff just so one screen can list assignable employees. For any "who can I assign this to / call this person" need, use `GET /auth/staff-roster?location_id=` instead (already unauthenticated-safe by design, since `LockScreen` calls it pre-login) — minimal fields, pre-filtered to `employee`/`counter_staff`/`florist_staff`, location-scoped. `SaleDetailScreen`'s task-assign modal was switched to this pattern 2026-09-01; reuse it rather than widening `GET /users`' `authorize()` next time this need comes up elsewhere.
- **`POST /api/sales/customer-order` (the customer self-order endpoint) is completely broken — 500s on every call.** Found live by `verify-order-flows.js` during the 2026-09-04 regression pass; confirmed pre-existing (byte-identical between this branch's HEAD and the working tree at the time it was found, so not a regression from any change described above). Root cause: the `INSERT INTO sales` statement in that route (`server/routes/sales.js`, search `customer-order`) lists 24 columns but its `VALUES (...)` tuple has 25 entries (19 `?` placeholders against only 18 bound args) — an off-by-one that fails at the DB layer for every request. Two more real gaps surfaced by the same pass, same route/area, also **not yet fixed**: (1) `customer-order` itself has no role restriction beyond `authenticate` — any staff role can call it too, not just `customer` — currently masked by the 500 above, would need its own `authorize()` once the crash is fixed; (2) separately, staff-facing sale creation (`POST /sales`, used by POS/counter checkout) trusts a client-supplied `unit_price` on a real product, bypassing the discount-approval threshold entirely — a price-manipulation gap, not a crash. Customer self-ordering is a hard-constraint feature (see "What this is" above) — this needs its own fix pass, deliberately kept out of scope here per user direction (flag only, not fixed this session).
- `GET /api/track/:token` (order-list-redesign work) is the app's first-ever public/unauthenticated route. A PR review flagged it had no rate limiting; fixed with a small self-contained in-memory per-IP fixed-window limiter local to `server/routes/track.js` (no new dependency). Rate-limited public routes today: `/api/track/*`, `/api/order-request/*` (including `open` and `status`), `/api/slip/*`, `/api/price/*` and `/api/auth/join*` — each with its own in-memory per-IP limiter, deliberately not sharing state (`trust proxy` is now set, so the IP is the real client's). Everything else, including every authenticated route, still has zero request-rate protection. The next person adding another public surface inherits that gap explicitly, not by accident.
- The `feature/order-list-redesign` branch (Deliveries redesign + customer tracking page, not yet merged) went through a whole-branch adversarial review 2026-09-11; all Important findings were fixed same session, but `docs/superpowers/specs/2026-09-11-order-list-redesign-deferred-findings.md` records everything deliberately left as-is (Minor findings) — read it before touching `DeliveriesScreen.js`, `OrdersInboxScreen.js`, `TrackingScreen.js`, or `ContactButtons.js` again. The tracking link is also **not customer-reachable in production yet** — see `VPS_DEPLOYMENT_GUIDE.md` §17 — the web build/hosting for `/track/:token` was never set up.
- **`TRACKING_LINK_SECRET` isn't set in `server/.env`, which makes one `verify-order-flows.js` check flaky across separate processes (not a real bug, but wastes time re-diagnosing it).** `server/utils/tracking-token.js` deliberately falls back to a fresh per-process `crypto.randomBytes` secret when the env var is unset. The multi-worktree norm this repo now uses (start this worktree's own dev server on its own port, run a verify script against it from a separate `node` process) means the server process and the script process each mint their own random secret — so the check that signs/verifies a tracking token in-process against a token the *live server* generated (`server/scripts/verify-order-flows.js`, search "GET /api/track/:token returns status-only data") fails with `got null` even though nothing is actually broken. Confirmed by reproducing it both ways on identical code/DB: 57/58 with mismatched per-process secrets, 58/58 once `TRACKING_LINK_SECRET` is exported to the same value before starting both the server and the verify script. Do this whenever running `verify-order-flows.js` against a separately-started server, or this one check will look like a regression every time.
