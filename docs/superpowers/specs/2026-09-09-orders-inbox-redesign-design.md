# Orders Inbox screen redesign — design

**Status:** revised after an adversarial Opus review found 3 Critical and several Important gaps in the first draft; awaiting user review of this revision.
**Sub-project:** first follow-on plan consuming the order-list-foundation toolkit (`docs/superpowers/specs/2026-09-05-order-list-screens-redesign-design.md`, `docs/superpowers/plans/2026-09-05-order-list-foundation.md`, PR #5 into `feature/identity-roles-pin-login`). Builds `app/src/screens/OrdersInboxScreen.js` against the toolkit's real, as-shipped interfaces.

## 0. What changed in this revision, and why

A review dispatched specifically to check this design against what was actually decided during brainstorming, and against real UX outcomes for non-technical staff, found genuine problems in the first draft — not code bugs (none of this had been built yet), design-level gaps:

1. **The "Share Tracking Link" idea is dropped from this plan entirely.** There is no tracking-page screen or deep-linking route anywhere in the app yet — the foundation plan only built the backend token/endpoint; the actual customer-facing page was deferred to a follow-on plan that doesn't exist. Shipping a button whose only outcome is WhatsApping a customer a dead `localhost` link is worse than not having the feature. Revisit this once that follow-on plan lands.
2. **The one-tap "next action" button is no longer a blind `api.advanceOrder` call.** The first draft's spec claimed this reuses "the same mechanism `OrderCard` already uses" — that was inaccurate. `OrderCard` (`app/src/components/orderBoard/OrderCard.js`) wraps the call in `resolvePreparerStep`/`resolveDeliverStep`, which intercept "Start Preparing" (may need a preparer picked) and "Mark Delivered" (may need a COD amount collected) before firing. Without that guard, tapping "Mark Delivered" on a COD order from a list row would mark it delivered with **zero cash recorded** — the exact "recomputed without the guard every sibling route has" bug shape this project has already had to fix repeatedly in register/settlement code. See §5.
3. **Day grouping and "Urgent first" sort compose badly, and the user has now made the call:** when `sort === 'urgency'` is active, grouping is suppressed entirely — a flat list, rush → soonest-scheduled → oldest, with no day/session headers. Grouping by `created_at` only applies under the default "Recent" sort. Confirmed with the user directly (not assumed): a flat urgency list beats trying to reconcile two incompatible orderings.
4. **The per-day-component grouping architecture was replaced.** The original approach (one small component per day, each calling `useRegisterSessions` itself, to satisfy React's hooks rules) technically worked but meant grouping couldn't be pre-computed synchronously — so it had to render as a plain `FlatList` of day-items rather than a real `SectionList`, defeating virtualization on exactly the search flow that's the user's #1 stated pain point. §2 now uses a single bulk-fetch hook instead, enabling one real `SectionList`.
5. **A pre-existing, previously-invisible backend bug is now in scope to fix.** `GET /sales`'s "total count" query (`server/routes/sales.js`) is a hand-duplicated second query that omits `search`, `pickup_status`, and non-owner location scoping — all filters the main query applies. Today's screen never looks at `total` at all (it silently caps at 100 rows), so this bug has never mattered. The moment this redesign relies on `total`/`hasMore` for real pagination, it becomes a real, user-visible "Load more does nothing, forever" bug on the single most common filtered/searched view. See §6.
6. **Status stays a visible, one-tap chip row; only Channel/Rush/Order Type move into the Filters drawer.** The bounded-toolbar pattern is the right fix for `DeliveriesScreen`'s 5-stacked-rows problem, but Orders Inbox never had that problem, and Status is this screen's single most frequent filter action. Moving it behind "open drawer → tap → close drawer" would cost 2 extra taps on the most common case for no real row-count savings, against CLAUDE.md's own "shortest path" principle. See §3.
7. **Order type joins the filter set** (the user explicitly named it as something they search/filter by; `GET /sales` already accepts an `order_type` param — this was simply missed in the first draft).
8. **The row layout changed** from "action button squeezed inside the narrow main text column, competing with two icon buttons" to a **full-width action row beneath both columns** — the first draft's math (a `flexShrink: 1` primary button against ~150dp of fixed-width secondary icons on a 360dp-wide phone) meant the button, not the icons, was the thing that shrank — the exact inversion of "one dominant action." See §5.
9. Several smaller, concrete fixes folded in because they were caught red-handed rather than argued for: `Alert.alert` is a documented no-op on the web build this shop actually runs (`app/src/utils/alert.js` exists specifically to fix this elsewhere) — use `showAlert`, not the raw API; a filter's "All" chip must actually highlight when nothing is selected (a `null`-vs-`undefined` comparison bug); the row's time display must show a real time, not a bare date; a visible search-clear (✕) button, present on today's screen, isn't allowed to quietly disappear; a failed background refresh must stay visible as an error even when the list already has items to show (not just when it's empty).
10. **Two things are named as explicitly deferred, not silently dropped:** searching by `vendor_name` (the user named it, but that field is deliberately owner-only-readable per this project's own prior work closing a leak of it through 5 other routes — adding it to a search clause every authenticated role can use needs its own careful pass, not a rushed addition here); and the still-live `wa.me` double-country-code-prefix bug on `OrderCard.js`/`SettlementsScreen.js` is fixed as a small, separate, self-contained task in the same plan (closes a decision the user made — "both coverage and quality" for Call/WhatsApp — that the foundation plan left half-finished).

## 1. Scope

This redesigns `app/src/screens/OrdersInboxScreen.js`, plus one small unrelated fix (item 10 above) and one backend fix (item 5 above) that this screen's own correctness depends on. It is the first real consumer of `useOrderListData`, `OrderListToolbar`, `FilterDrawer`, `ActiveFilterChips`, `ContactButtons` — establishing the integration pattern Deliveries and Pickup Orders follow-on plans will reuse. `OrdersHubScreen.js`'s tile-count fix already shipped in the foundation PR; every other screen is untouched.

## 2. Data & grouping model

`useOrderListData(fetchFn, { pageSize: 50 })` where:
```js
const fetchFn = (params) => api.getSales(params).then((r) => ({ items: r.data.sales, total: r.data.total }));
```

**Grouping has three states, computed fresh on every render from the currently-loaded page — no new backend endpoint beyond §6's fix:**

1. **`sort === 'urgency'`:** no grouping at all. One flat section, in the order the server already returns (rush → soonest-scheduled → oldest-pending). Confirmed with the user: reconciling urgency-sort with day-grouping isn't worth the complexity or the risk of burying the one thing that's actually urgent under an old date header.
2. **Default sort, single location:** day grouping (shop-timezone-aware, via the new `extractShopDateKey`/`groupOrdersByDay`), and within each day, sub-grouping by register session via `groupOrdersBySession` — but this needs every distinct day's sessions fetched *before* sections can be built synchronously (a real `SectionList` needs its sections known up front, unlike a `FlatList` of arbitrary items). **`useSessionsForDates(locationId, dateKeys)`** is a new hook that fetches every needed day's sessions in one `Promise.all` inside a single `useEffect` — a genuinely different mechanism from the already-shipped `useRegisterSessions` (which is scoped to one day and is itself a real hook, so it cannot be called in a loop over however many distinct days are on screen — the reason a per-day wrapper component existed in the first draft, and the reason it's gone now: this hook makes plain async calls to `api.getRegisterSessions` in a loop instead of calling a hook in a loop, which is what makes pre-computing all sections before render possible).
3. **Default sort, mixed locations (an owner viewing "All Locations"):** day grouping only, no session sub-header, ever — determined by `getSingleLocationId(orders)` finding more than one distinct `location_id` in the currently-loaded page. This is a data-driven check, not a role check or a location-picker UI — no new filter/picker is added for this; it's simply absent whenever the fetched page happens to span more than one location.

Rendered as one real `SectionList` (not a `FlatList` of day-items, which was the first draft's mistake): sections are computed via a `useMemo` keyed on `(list.items, list.sort, singleLocationId, sessionsByDate)`, each section carrying `{ key, dateLabel, sessionLabel, totalAmount, data }` — `totalAmount` is the section's own `grand_total` sum (a small new pure helper, `sumGrandTotal`, alongside the existing grouping functions), passed to `DateSessionHeader`'s already-supported `totalAmount` prop, which the first draft built but never wired up.

**Known, accepted, named limitation:** `useSessionsForDates` refetches on every dependency change rather than caching indefinitely — deliberately, to avoid repeating the exact "cache never invalidates after a mid-shift register close/reopen" bug the first draft's per-day approach would have inherited from `useRegisterSessions`'s own module-level cache. The residual gap: if a staff member never navigates away from this screen for an entire register session change, the session grouping won't refresh until they do (navigating to `SaleDetail` and back, or any other focus-loss/regain, refetches fresh). Accepted as a narrow, named edge case rather than engineered away.

## 3. Toolbar & filters

- **Status stays a visible, always-shown single row of chips** — exactly as today, one tap to change. This is the single most frequent filter action on this screen; per CLAUDE.md's "shortest path" principle, it doesn't move.
- `OrderListToolbar` (search + Filters button; no `viewModeProps`) with `sortProps` wired to `useOrderListData`'s `sort`/`setSort`: `options: [{ value: null, label: 'Recent' }, { value: 'urgency', label: 'Urgent first' }]`. Default stays `null` — never auto-selected.
- `FilterDrawer` sections — Channel, Rush, and **Order Type** (the user explicitly named order type as something they filter/search by; `GET /sales` already accepts `order_type`, this was simply missing from the first draft):
  - Channel: `[null, 'whatsapp', 'email', 'website', 'walk_in', 'phone']`
  - Rush: a single-entry toggle section
  - Order Type: `[null, 'walk_in', 'pickup', 'delivery', 'pre_order']`
- `ActiveFilterChips` rendered below the toolbar, driven by `useOrderListData`'s `filters`/`setFilter`/`clearFilters` — covers Channel/Rush/Order Type (Status has its own always-visible row and doesn't need a duplicate chip). Shows "Clear all" whenever more than one of these three is active.
- The search box keeps a visible ✕ clear button when non-empty — present on today's screen, not allowed to quietly disappear just because the box moved into `OrderListToolbar`.
- `route.params?.status` seeding (the Dashboard's "Done" chip lands here pre-filtered) is preserved exactly: on mount, if `route.params.status !== undefined`, call `setFilter('status', route.params.status || undefined)` once. The existing re-sync effect (status arriving again while the screen is already mounted) is preserved the same way.

**Explicitly deferred, not silently dropped:** searching by `vendor_name`. The user named it, but that field is deliberately owner-only-readable (closed after an earlier pass found it leaking unstripped through 5 other routes and an audit-log blob) — adding it to `GET /sales`'s search clause, which every authenticated staff role can use, needs its own careful pass to avoid quietly reintroducing that exact leak (even without displaying the field, being able to *filter by* it can indirectly reveal vendor associations). Not attempted in this plan.

## 4. Row redesign

Each row gains, over today's rendering:
- `location_name` (currently invisible when viewing "All Locations").
- The order's actual time — `formatTime(item.created_at)`, not `formatCardDateTime` with no time argument (which silently renders only a date; the first draft's own plan text had this bug).
- **A full-width actions row beneath both the main content and the side (stage/amount) column** — not squeezed inside the narrow main-text column, which is what produced the first draft's layout bug (three 44pt-wide controls fighting a `flexShrink: 1` primary button for ~180dp of space on a 360dp-wide phone). This row holds, left to right: the one-tap next-action button (when safe to show, see below) and `ContactButtons` (Call + WhatsApp).
- **The one-tap next-action button only renders when it's genuinely safe to fire with no other input**, per §0 item 2. Concretely: `nextAction` renders as a button only when `nextAction.body?.status !== 'preparing'` AND `!nextAction.endpoint?.endsWith('/deliver')` — i.e., never for the two cases (`resolvePreparerStep`/`resolveDeliverStep`, already exported from `OrderCard.js`) that might need a preparer picked or a COD amount collected first. For those two cases, no inline button renders at all — the row's existing tap-to-`SaleDetail` behavior is the correct path, since `SaleDetailScreen` already has the full, safe resolution flow (picking a preparer, collecting a COD amount) built and reviewed. This avoids building a second, parallel copy of that UI here, and never risks silently skipping the guard.
- `ContactButtons` built from `[{ label: 'Customer', phone: item.customer_display_phone || item.customer_phone }, { label: 'Recipient', phone: item.receiver_display_phone }]`. `context.type` maps `item.display_stage.key` through the two stage-specific templates `contact.js` defines (`'ready_for_pickup' → 'order_ready_pickup'`, `'out_for_delivery' → 'order_out_for_delivery'`), falling back to `'general_inquiry'` for every other key (already `buildMessage`'s own default). `context.params: { sale_number: item.sale_number, location_name: item.location_name }`.
- Any failure from the next-action call (e.g. a plain-language 400 from the server) surfaces via `showAlert` (`app/src/utils/alert.js`), never the raw `Alert.alert` — that API is a documented no-op on the web build this shop actually runs, and every sibling screen already uses `showAlert` for exactly this reason.
- Minimum 44×44pt tap targets, matching every other icon/button the foundation work already shipped.

**A failed background refresh must stay visibly an error, not silently vanish.** The first draft only rendered `list.error` inside the empty state (visible only when there are zero items to show) — meaning a refresh that fails over an already-populated list showed nothing wrong at all, leaving a staff member looking at stale data believing it's current. This revision renders a small, dismissable error line whenever `list.error` is truthy, regardless of whether `list.items` is empty or not.

## 5. Next-action safety (new section, was missing from the first draft)

`resolvePreparerStep({ order, tasks, viewerRole, viewerId })` and `resolveDeliverStep({ order })` are already exported from `OrderCard.js` — this plan imports and reuses them directly rather than re-deriving the same logic a second time (which is exactly the kind of drift this project has already paid for once). `resolvePreparerStep` needs a `tasks` array (the order's production tasks) that the list endpoint (`GET /sales`) does not return — only `open_task_count`, a number, is available on a list row. Rather than adding a per-row extra fetch to make the full inline resolution possible (expensive on a list screen, and duplicating `SaleDetailScreen`'s own already-built modal UI), this screen simply never attempts inline resolution for the two cases that might need it — see §4. The button only ever fires the simple, always-safe path: a `nextAction` with no ambiguity, or a `resolvePreparerStep` result of `'self'` (an `employee` viewer, exactly one unassigned task, no picker needed — safe to pass `assigned_to` directly, matching what `OrderCard`'s own `onQuickAction(order, { assigned_to })` path does).

## 6. Backend fix: `GET /sales`'s total-count query must mirror the real query

`server/routes/sales.js`'s count query (`let countSql = 'SELECT COUNT(*) as total FROM sales s WHERE 1=1'; ...`) is a second, hand-duplicated copy of the main query's filter-building logic that is missing `pickup_status`, `filter_date`, `search`, and the non-owner location-scoping block the main query applies (lines 246-252). Today's screen never uses `total` (it silently caps at a fixed row limit), so this bug has been invisible. The moment real pagination depends on `total`/`hasMore` being accurate, it becomes a real, user-facing "Load more does nothing, forever" bug — specifically on the search flow, which is the user's #1 stated pain point.

**Fix, matching the same pattern already used for `GET /deliveries`'s count in the foundation plan:** snapshot the main query's `sql`/`params` right before `ORDER BY` is appended, and compute `total` from `SELECT COUNT(*) FROM (${sql}) as sub` against that exact snapshot — eliminating the separate hand-written `countSql` block entirely, so there is only ever one place this filter logic lives.

## 7. Pagination

Real "Load more": a `SectionList` `ListFooterComponent` showing a button when `hasMore` is true, calling `loadMore()`, disabled/hidden while `loading`. Depends on §6's fix to actually work under a search or non-owner-location-scoped view — the first draft's version would have appeared correct in casual testing (an unfiltered owner view happens to compute the same `total` both ways) and only failed on the exact flow it needed to work on.

## 8. Explicitly unchanged

- The quick-links row (Pickup Orders / Deliveries) and secondary Customers FAB, both `employee`/`counter_staff`-only — untouched, including their exact role gate.
- The primary Log Order FAB — untouched.
- `OrdersHubScreen.js`'s tile-count fix — already shipped in the foundation PR, not part of this plan.
- `PickupOrdersScreen.js` and `DeliveriesScreen.js` — separate follow-on plans, not touched here.

## 9. Testing / verification approach

No screen-render test harness exists in this codebase. Verification is `node scripts/babel-check.js` per touched/created file, `app/scripts/verify-*.js` (plain Node `assert`) for every pure function, a new backend regression check for §6's fix, and a live manual trace through the actual running app as an explicit final task step — covering every flow named in §0-§7 above, not just the ones that were already correct in the first draft.

## 10. Explicitly out of scope / deferred

The public tracking page itself and the "Share Tracking Link" action that depends on it (§0 item 1 — revisit once that follow-on plan exists); searching by `vendor_name` (§3, a deliberate security-scoped deferral, not an oversight); Deliveries and Pickup Orders screens (separate follow-on plans); any filter dimension beyond Status/Channel/Rush/Order Type; per-row extra fetches to enable full inline preparer/COD resolution (§5 — the existing `SaleDetailScreen` flow is reused instead); multi-location session matching for the owner's "All Locations" view (§2).
