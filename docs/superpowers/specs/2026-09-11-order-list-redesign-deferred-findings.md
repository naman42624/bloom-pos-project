# Order-list redesign — deferred findings (whole-branch review, 2026-09-11)

**Purpose of this doc:** a dispatched adversarial review covered the completed Deliveries redesign (`docs/superpowers/specs/2026-09-10-deliveries-redesign-design.md` + its own follow-on bulk-actions sub-plan) and the customer tracking page (`docs/superpowers/specs/2026-09-11-customer-tracking-page-design.md`) against their specs/plans. No Critical findings in either — the safety-critical "never fire a mutating action blind" logic was traced and confirmed correct in both. The review's Important findings (A1, A2, A3, A5, B2, B4, B5) plus two user-decided items (A4, B1) were fixed the same session — see the commits on `feature/order-list-redesign` dated 2026-09-11 (`dc53013`, `858c992`, `5888426`, `cdec4d5`, `4bc4481`).

**This doc is the record of what was *not* fixed** — the review's Minor-severity findings, each judged safe to leave as-is for now. Read this before touching the affected files again; a few of these compound into real bugs (A13 especially) once someone builds on top of them without knowing they're there.

## Deliveries (`app/src/screens/DeliveriesScreen.js`)

- **A6 — No pagination UI.** `useOrderListData` is wired with `pageSize: 200`, and the plan's own task claimed pagination was verified, but there's no "load more" control or infinite-scroll trigger in the screen — a shop with more than 200 in-scope deliveries would silently never see the rest. Low real-world risk today (a single shop rarely has 200+ open deliveries at once) but worth a real fix (or at minimum a "showing 200 of N, narrow your filters" banner) before this becomes a live gap.

- **A7 — Status-tab chip row is sub-44pt.** `styles.tab` (`paddingVertical: 8` + ~14-16px text) works out to roughly 30-32pt tall, under the 44×44pt minimum tap target staff-ux-checklist #7 calls for. Pre-existing (not introduced by this redesign) and deliberately kept per the design spec's own acceptance — the spec explicitly scoped tap-target enforcement to the *new* controls it introduced, not a retrofit of every pre-existing one. Worth folding into a future UI-pass sub-project (CLAUDE.md roadmap item 9), not a one-off fix here.

- **A8 — Double-fetch on mount/focus, shared with Orders Inbox.** Both screens can end up firing two initial fetches in quick succession (one from `useOrderListData`'s own mount effect, one from the screen's `useFocusEffect(list.refresh)`). Harmless today — `useOrderListData`'s request-race protection means the correct response always wins — but it's a real wasted round trip on every screen open, not just a theoretical one. A `useOrderListData`-level fix (skip the auto-mount fetch when the caller already triggers one via `useFocusEffect`) would fix this once for every future consumer (Pickup Orders included) rather than per-screen.

- **A9 — Half-cleared date-range filter chip.** Confirmed still present: `ActiveFilterChips`' `onRemove(key)` (`DeliveriesScreen.js`, the `filters={{ ...date_from: ..., date_to: ... }}` block) only clears the one key tapped — removing just the "From: X" chip leaves "To: Y" active with `dateRangePreset` reset to `null` (no preset highlighted, but a real one-sided filter still applied silently). Fix would be: removing either date chip clears both `date_from` and `date_to` together, since the UI only ever offers them as a paired preset in the first place (no control lets a user pick only one side).

- **A10 — Route-assignment endpoints aren't location-scoped.** `PUT /deliveries/:id/route` and `POST /deliveries/batch-assign-route` (`server/routes/deliveries.js`) don't filter by `location_id` — confirmed by inspection, no `location_id` reference in either handler. This mirrors a pre-existing identical gap in `/batch-assign` (rider assignment), so it's consistent with today's model rather than a new hole this redesign introduced, but it means a manager scoped to one location could technically assign a route to a delivery at another location if they knew its ID. Worth closing both gaps together in one pass rather than fixing route-assign in isolation.

- **A11 — Misleading "Success" alert on 0-assigned.** `handlePickRiderConsolidated`/`handleConfirmRouteAssign`'s batch branches show `showAlert('Success', res.message || ...)` unconditionally on a 200 response, even if the backend's own response indicates 0 deliveries were actually assigned (e.g. every selected id was already terminal-status and got skipped). The response shape would need checking (does `batchAssignDeliveries`/`batchAssignRoute` return an assigned-count distinct from the requested-count?) before this can distinguish "assigned N" from "assigned 0 of N" — flagged, not investigated further.

- **A12 — Dead styles.** `styles.assignBtn`/`assignBtnText` (`DeliveriesScreen.js`) are defined but no longer referenced anywhere in the file — a leftover from before the rider-assignment UI was consolidated onto `AssignPickerModal`. Safe to delete whenever this file is next touched for something else; not worth a standalone commit.

- **A13 — Three divergent copies of the same safe-action predicate.** `resolvePreparerStep`/`resolveDeliverStep` (exported from `app/src/components/orderBoard/OrderCard.js`) are the authoritative "is it safe to fire this action blind, or does it need a picker/inline prompt" logic, and `OrderCard.js` itself imports and calls them directly. Confirmed by inspection: neither `DeliveriesScreen.js` nor `OrdersInboxScreen.js` actually imports them — both only *mention* them in comments and reimplement the same predicates inline (`needsPreparerPick`, `needsCodCollect`, computed by hand against `has_unassigned_open_task`/`cod_amount`/`cod_collected`). All three copies happen to agree today, but this is exactly the "one conceptual value computed two different ways" pattern this codebase has already been bitten by in register/settlement math (see `CLAUDE.md`'s "Known structural debt"). The next person who changes the underlying rule (e.g. a new precondition for safe COD collection) has to remember to update three places, not one. A real fix means adapting `resolvePreparerStep`/`resolveDeliverStep` to accept the two screens' `toSaleShape`-adapted rows (Deliveries) and native `GET /sales` rows (Orders Inbox) through one shared interface, then importing them for real in both — worth doing as its own small task before this drifts further.

- **A14 — `ContactButtons` doesn't call `stopPropagation` internally, and neither call site wraps it.** Confirmed by inspection of `ContactButtons.js`: its Call/WhatsApp `TouchableOpacity`s call `onPress={() => handlePress(...)}` with no `e.stopPropagation()`, and both `DeliveriesScreen.js` and `OrdersInboxScreen.js` render `<ContactButtons .../>` directly inside the card's own `TouchableOpacity` with no wrapping stop-propagation handler either — unlike every other in-card action button in both files, which explicitly does `onPress={(e) => { e.stopPropagation(); ... }}`. On native this is usually harmless (nested touch responders don't typically bubble to the outer one), but on web (`react-native-web`, where this app also targets `Platform.OS === 'web'`), click events bubble through the DOM by default — so tapping Call/WhatsApp on a card likely *also* fires the card's own `onPress` (navigating to the detail screen) on web specifically. Fix belongs inside `ContactButtons.js` itself (one `stopPropagation` call covers every screen that uses it), not per call site.

## Customer tracking page (`app/src/screens/TrackingScreen.js`, `server/routes/track.js`)

- **B3 — Step-marker "done" vs. "current" style diverges from the plan's stated acceptance criteria.** The plan's own testing section describes a specific visual distinction between a completed step and the current one; the shipped visual-redesign commits (`38f90e8`, `cce4f9e`) landed a different but arguably *safer* treatment (current step more visually prominent than done steps, rather than the plan's originally-described balance). Not a functional bug — flagged only because it's a documented spec/implementation mismatch worth a conscious decision (update the spec to match reality, or restyle to match the spec) rather than leaving the two silently disagreeing.

- **B6 — Tracking tokens never expire and can't be revoked.** `tracking-token.js`'s HMAC signing has no timestamp/expiry embedded and no revocation list — a link generated today works forever, and there's no way to invalidate one early (e.g. if accidentally sent to the wrong number). Accepted within this feature's stated threat model (a link is low-sensitivity: sale number, coarse status, scheduled date/time, location name — no money, address, or phone data per the design doc §1). Worth reconsidering only if the returned fields ever expand to anything more sensitive.

- **B7 — The public tracking page ships the whole staff JS bundle.** `TrackingScreen.js` is carefully isolated at the *runtime* level (no `AuthContext`/navigation dependency, confirmed safe to render standalone — see `App.js`'s routing bypass and the design doc §3), but it's still bundled and shipped as part of the same JS bundle as the authenticated staff app, not code-split separately. An unauthenticated visitor's browser downloads the whole app's code to render one small public page. No security exposure (nothing sensitive is *in* the bundle beyond what any staff member's browser already has anyway, and no additional attack surface is opened — runtime isolation is what actually matters for safety), but a real, unaddressed load-time/bandwidth cost for a customer opening a tracking link on mobile data.

- **B8 — The 5-step delivery ladder wraps mid-word on narrow viewports.** `TrackingScreen.js`'s `stepsRow`/`stepLabel` layout (5 steps for a delivery order: Order Received → Preparing → Ready → Out for Delivery → Delivered) hasn't been checked against genuinely narrow phone viewports (e.g. an older/smaller Android device) — "Out for Delivery" is the longest label and the most likely to wrap awkwardly. Cosmetic only, not investigated further this session.

- **B9 — Today/Tomorrow date labels are derived device-locally, not shop-timezone-aware, on this one page.** `formatShopDateLabel` is imported and used correctly for the actual date value, but the "Today"/"Tomorrow" framing itself resolves against the *visiting device's* local clock, not the shop's configured timezone — a customer viewing the page from a different timezone than the shop could see a date framed as "Tomorrow" when it's actually "Today" shop-side, or vice versa. This is a pre-existing pattern across the whole app (not unique to this page — see `DeliveriesScreen.js`'s own `getTimeInfo`, which has the identical characteristic), so fixing it here alone wouldn't close the gap app-wide. Worth a dedicated pass across every screen that does this, not a one-off patch on the public page.

## Suggested triage for whoever picks these up next

Cheapest wins if this list is ever worked: **A12** (delete dead styles, zero risk), **A9** (clear both date keys together), and **A14** (one `stopPropagation` call inside `ContactButtons.js`, fixes both screens at once) are all small, low-risk, single-file fixes. **A13** is the one worth prioritizing despite being "just" a Minor finding — it's a structural debt pattern this codebase has paid for before, and it only gets more expensive to unwind the longer three copies of the same rule keep existing. The rest (A6, A7, A8, A10, A11, B3, B6, B7, B8, B9) are all fine to leave exactly as they are until something else forces the file open.
