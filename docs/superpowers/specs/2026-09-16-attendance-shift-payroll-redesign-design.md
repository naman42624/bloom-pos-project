# Attendance, shift, overtime & payroll redesign — design

**Sub-project:** roadmap item 6 (Attendance & shift management), extended per user direction to also cover salary/payroll/advance tracking (roadmap didn't previously list this as its own item — the two are folded into one design here because they share a data model: overtime cannot be computed without shift segments, and payroll cannot be trusted without correct attendance).

## 0. Why this exists

The owner's own words: "the shift and attendance is a mess... not usable in the current state... a lot of small bugs." An investigation (this session, static code read of `server/routes/attendance.js`, `server/routes/staff-management.js`, all five attendance/salary screens, `MainNavigator.js`, and the live dev DB) found the picture is more specific than "nothing works": a substantial, mostly-working payroll subsystem already exists end-to-end (shifts, salaries, payroll calculate/disburse, salary advances, real geofencing), but it has two confirmed live bugs, one role silently locked out of three routes, a data model that cannot represent split shifts correctly despite having a field for them, and an information architecture that buries payroll/advances/shifts equally deep regardless of how often they're actually used. This document redesigns around those specific findings, not a generic rewrite.

## 1. What already exists (verified, not assumed)

- **Attendance** (`attendance.js`): row-per-session model (supports multiple clock-in/outs per day already, mechanically — the `/clock-in` guard only blocks a *second open* session, not a second session per day), `late_arrival`/`early_departure` booleans computed at clock-in/out time via `isLateArrival()`/`isEarlyDeparture()`, GPS coordinates captured on manual clock-in/out, outdoor-duty request flow, salary-advance request flow.
- **Shifts** (`staff-management.js` `/shifts`): per-user-per-location shift row including `shift_segments` (JSON, for split shifts) — **defined and displayed in `ShiftManagementScreen.js`, but never read by any attendance or payroll logic.** This is the central gap this design closes.
- **Payroll** (`staff-management.js` `/salaries`, `/payroll/*`): salary records with type (monthly/daily/hourly), salary-change history, a preview-only `/payroll/calculate`, a transactional `/payroll/disburse` (writes `salary_payments`, auto-deducts outstanding `salary_advances` oldest-first), paginated `/payroll/history`. Fully wired to `SalaryManagementScreen.js`.
- **Salary advances**: request/approve/reject/repay flow, `SalaryAdvancesScreen.js`, already auto-deducted during disbursement.
- **Geofencing — mechanism exists, does not currently work.** Per-location `geofence_radius`, native background geofencing (`useGeofence.native.js`) + web geolocation watch (`useGeofence.js`), a server cron (`server.js`) that auto clocks someone out after a configurable per-shift timeout following an exit event, are all real code. But a post-design-review pass against the live dev DB (2026-09-16) found this has never actually fired: `geofence_events` holds **zero rows**, ever. Root cause: `locations.latitude`/`longitude` are `NUMERIC(10,2)` — two decimal places is a ~1.1km grid at this latitude, while `geofence_radius` is 50m, so the stored "shop center" can sit up to ~780m outside its own geofence circle. An earlier draft of this section asserted "Main Shop has real coordinates and a tuned radius" — true of the data being present, false of it being precise enough to trigger anything; that was this document's own error, corrected here rather than carried forward. §3/§4 now include fixing this for real.
- **Push notifications**: fully built (`push_tokens` table, `createNotification({ userIds, title, body, ... })` in `notifications.js`, already used by `sales.js`/`deliveries.js`/`production.js`). No new infrastructure needed anywhere in this design.
- **Navigation**: all six attendance/salary screens are registered and reachable (not orphaned) — but five of six are one level deep, behind a "Quick Links" row inside `AttendanceScreen`, with no frequency-based prioritization (a screen used once a month is exactly as buried as one used daily).

## 2. Confirmed bugs (fixed regardless of anything else in this doc)

1. **`salary_advances.status` CHECK constraint** doesn't include `'repaid'`, but `staff-management.js` (`/payroll/disburse` auto-deduction) and `attendance.js` (`/attendance/salary-advance/:id/repay`) both write exactly that value. Confirmed in the live dev DB: the constraint is **already absent there** — meaning dev was hand-patched at some point and the fix never became a `database.js` migration, the identical pattern that already caused two real production 500s in this codebase (`refunds.requested_by`/`approved_by`, `users_role_check` — see `CLAUDE.md`'s structural-debt section). If production still has the original constraint, marking an advance repaid or disbursing payroll against someone with an outstanding advance is 500ing there right now.
2. **`florist_staff` excluded from `authorize()`** on more routes than first found — the original pass here undercounted at "three routes"; a full grep of every `authorize()` call in `attendance.js`/`staff-management.js` (done during plan-writing) found **10**: `GET /attendance/today`, `POST /attendance/outdoor-duty`, `PUT /attendance/outdoor-duty/:id/complete`, `GET /attendance/outdoor-duty`, `POST /attendance/salary-advance`, `GET /attendance/salary-advances`, `GET /staff/shifts`, `GET /staff/salaries`, `POST /staff/geofence-event`, `GET /staff/payroll/history`. Three of these (`GET /outdoor-duty`, `GET /salary-advances`, `GET /shifts`) also have an *internal* role-scoping array that needs the identical fix — without it, passing the outer `authorize()` gate alone would let a florist_staff see every other employee's data, a leak, not just a fix. A further review pass (2026-09-16) found the same gap survives in two more places the `authorize()` sweep didn't touch at all: `GET /attendance/staff-today`'s "who hasn't clocked in" query (`attendance.js`, the `notClocked` subquery's role `IN (...)` list) and `GET /staff/salaries`' owner-view role list — both hardcode `('employee', 'counter_staff', 'delivery_partner'[, 'manager'])` with `florist_staff` absent, meaning a florist is invisible on the very roster this redesign builds and cannot be enrolled in payroll at all. Every failure here is caught client-side and swallowed (no error shown) — a florist's own status/advances/geofence/payroll tracking just silently doesn't work or doesn't show them, with no signal to anyone that anything's wrong.
3. **`isLateArrival()`/`isEarlyDeparture()` compare against a single `shift_start`/`shift_end`, always** — regardless of `shift_segments`. A split-shift employee (e.g. 7–12, 6–10) clocking in for their second session gets compared against the *first* segment's start time: 18:00 > 07:00 evaluates to "late," every day, for arriving exactly on time. This is a correctness bug, not a UX gap — it's why the attendance data itself can't be trusted for anyone on a split shift today.

## 3. Scope

**In scope:** shop-bound staff attendance (owner, manager, employee, counter_staff, florist_staff), shift definition including split shifts, overtime *tracking* (not auto-pay), salary/payroll/advances, and the information architecture around all of it.

**Added to scope after the post-design review (2026-09-16, all four confirmed directly):**
- **A clock-out recovery sweep.** The review's live-data check found the *actual* dominant real-world failure isn't "forgot to clock in" (this document's original focus) — it's forgotten clock-**outs**: 6 sessions in the dev DB are still open, one since June, because the exit-timeout auto-clock-out depends on the employee's phone still running the background task, which stops working the moment the app is force-quit or the battery dies. A server-side end-of-day sweep now closes any session still open N hours past its matched shift-segment end, marked distinctly (`clock_out_method = 'auto_shift_end'`) and surfaced to the manager for confirmation rather than silently trusted.
- **Fixing `locations`/`attendance`/`geofence_events` latitude/longitude precision.** `NUMERIC(10,2)` → `NUMERIC(9,6)` on all three tables' lat/long columns — this is what makes geofencing (see §1's correction above) capable of working at all. This is a type change, not a new nullable column, so it needs the explicit sign-off `db-migration-safety` requires for anything beyond additive — given directly, this session, in response to being asked. Existing stored coordinates lose no additional precision by widening the column (2 decimal places survive unchanged in a wider numeric type) — the precision that's already lost is in the *values themselves*, which must be re-entered with real precision after this ships; the migration alone doesn't fix data that was never precise.
- **Salary advances get the same expense/register linkage as disbursement.** The original draft of this document justified `expenses.employee_id` partly as "closing the advances aren't connected to reporting gap" but never actually wired advance *approval* to write anything — a real gap against the user's original ask that advances and salary need to be connected. `PUT /attendance/salary-advance/:id/:action` (approve) now gets the same register-guard + linked-expense treatment `POST /payroll/disburse` gets (§ new section below).

**Explicitly still out of scope:**
- **Delivery riders.** They have a separate live GPS delivery-tracking system already and a fundamentally different work pattern (mobile all day, not shop-bound). They keep using clock-in/out exactly as today; nothing here changes for that role.
- **Overtime auto-pay.** This design computes and surfaces OT; it never factors OT into `net_amount` automatically. Revisit as a separate, explicitly-scoped follow-up once tracking has been live long enough to trust the numbers.
- **Geofence radius/timeout tuning** as an ongoing operational concern (picking the "right" 50m vs 100m per shop) stays a judgment call for the owner, not something this design prescribes — distinct from the precision *fix* above, which is a correctness bug, not a tuning choice.
- Anything about `ShiftManagementScreen.js`'s own editing UI beyond what's needed to make split shifts actually take effect downstream — the segment-entry UI itself already works and isn't being redesigned, just finally connected to something that reads it.

## 4. Data model changes (all additive; see `db-migration-safety` review below)

| Table | Change | Why |
|---|---|---|
| `expenses` | new nullable `employee_id` (FK → `users.id`) | Lets a salary-category expense — auto-written or manually entered — link to a real employee, closing the "advances and salary aren't connected to reporting" gap. |
| `salary_payments` | new nullable `expense_id` (FK → `expenses.id`) | Traceability in both directions between a payroll disbursement and its expense/register-reconciliation record. |
| `salary_advances.status` CHECK constraint | widened to include `'repaid'` | Fixes bug #1 above. Widening-only — cannot reject any row the old constraint accepted. |
| `locations.latitude`/`longitude` | `NUMERIC(10,2)` → `NUMERIC(9,6)` | Makes geofencing capable of working at all (§1, §3). A type widen, not additive in the strict "new column" sense — explicit sign-off given this session per `db-migration-safety`. |
| `attendance.clock_in_latitude`/`clock_in_longitude`/`clock_out_latitude`/`clock_out_longitude` | same widen | Same reasoning — captured positions are equally imprecise today. |
| `geofence_events.latitude`/`longitude` | same widen | Same reasoning. |

**No new columns on `attendance`, `employee_shifts`, or any other table** beyond the precision widen above (which changes an existing column's type, adds nothing new). Earlier drafting of this design considered a new `scheduled_segment_index` column and a stored `late_minutes` value; both turned out unnecessary once late-minutes and OT-minutes were designed as read-time derivations (§6) from data already stored (`clock_in`/`clock_out` timestamps, `shift_segments`) — matching how `computeOrderStage()` already works in this codebase (computed fresh, never stored, so it can't go stale if a shift definition changes later). Leaner migration, same outcome.

**Migration mechanics:** `ensureColumn`/constraint-patch calls in `database.js`, idempotent, following the exact existing pattern (compare to the `purchase_orders_status_check` drop-and-recreate already in that file). Per `db-migration-safety`: before any of this runs against production, take a backup and confirm against a copy of real data, not just the empty/synthetic dev DB — this is an implementation-phase step, tracked in the plan, not done as part of this design. The `NUMERIC` type widen specifically needs a backup taken first regardless of how routine it looks, per the explicit sign-off given for it.

**Layering note — corrected.** An earlier draft of this section claimed the new `expenses` insert inside `POST /payroll/disburse` needed to share a transaction with the existing `salary_payments` insert "so both commit or neither does," and used that to justify staying on the sync `getDb()` layer. That claim was wrong: a direct read of `database.js` found `db.transaction(fn)` is `return (...args) => fn(...args)` — **a no-op, not a real transaction** — every statement still runs through its own `spawnSync('psql', ...)` subprocess on its own connection, autocommitted individually. `database-async.js`'s version does issue real `BEGIN`/`COMMIT`, but the callback's own statements go through the pool rather than the transaction's dedicated client, so it isn't atomic either. Given neither layer actually provides atomicity here, the real design requirement is ordering the writes so a failure midway does the least damage, not which layer to use: write the `expenses` row **first**, then `salary_payments` with `expense_id` already resolved — if the expense write fails, no payment is recorded as paid; if the payment write fails after a successful expense write, that's a harmless orphaned expense row, not a payment silently marked paid with no way to undo it.

## 5. Employee-facing changes

The clock-in/out control itself — button, screen, position — **does not move**. Per `staff-ux-checklist`, this is the highest-frequency action in the whole domain (up to twice a day, every day, for someone who's never used business software before); the redesign's IA changes (§7) are entirely on the manager/owner side. What changes underneath:

- **Split-shift correctness** (fixes bug #3): `isLateArrival()`/`isEarlyDeparture()` resolve the *nearest* segment when `shift_segments` is set, falling back to today's single-window behavior when it isn't — someone without a split shift sees zero change in behavior.
- **Geofence auto-clock-in stays fully automatic** (per direct confirmation — no added tap, no daily overhead), but stops being silent: `createNotification()` fires immediately after, e.g. *"Clocked in automatically at Main Shop, 9:03 AM"*, with a one-tap **Undo** for the rare mis-fire (walked past the shop, arrived early off-duty). **Undo is time-bounded to 15 minutes after the auto-clock-in** — a full day's attendance disappearing on one tap with no confirmation, hours after the fact, is not "low-stakes and reversible" the way a same-minute correction is; past the window the banner stops offering it and a manager fixes it manually instead (same one-tap roster action §7 already provides). Exit-timeout auto-clock-out is unchanged — still fully automatic, no notification needed since there's no ambiguity to resolve on that side (per the user's own framing: "not to replace the tap" was specifically about arrival, not departure). **The auto-clock-in trigger itself gains a server-side proximity check**: `POST /staff/geofence-event` currently trusts the client's claimed `event_type` with no verification — any authenticated staff member could `POST` a fake "enter" from anywhere. The route now recomputes the haversine distance between the reported coordinates and the location's own (now-precise, per §4) coordinates, and rejects if outside the radius.
- **A real recovery path for a missed clock-in**: today, forgetting to clock in just leaves someone wrong for the day with no self-service fix. New: a plain-language shortcut ("Didn't get a chance to clock in? Let your manager know") that sends one manager-facing notification rather than requiring the employee to track someone down in person.
- **Visibility into their own record, today**: a plain-language line on their own Attendance screen — *"You're 20 minutes into overtime"* / *"Clocked in 8 minutes late today"* — using the same read-time computation as §6. This directly answers the audit finding that the current flow is entirely a pull (nothing surfaces proactively) and closes the "no feedback loop" gap. Not sensitive data in the `CLAUDE.md` cost/margin sense — it's an employee's own work record.

## 6. Overtime & late-time computation

A pure function (mirrors the shape of `server/utils/order-stage.js`'s `computeOrderStage()`), taking a day's attendance sessions and an employee's `shift_segments` (or single `shift_start`/`shift_end` as fallback), returning:

- Worked time per matched segment.
- **Late minutes**: `clock_in − matched segment start`, when positive — not just the existing boolean, the actual delta.
- **Overtime minutes**: time worked past a segment's end, **minus a 30-minute grace period**, floored at zero. Applies uniformly to every segment boundary in the day (not only the last one) — a split-shift employee who runs 20 minutes over their midday segment end isn't flagged any differently than someone who runs over at closing; both are inside the 30-minute grace, so neither counts.

**Segment-matching is overlap-based, not nearest-start-based — corrected during plan review.** An earlier draft of this design matched each session to whichever segment's *start* time was numerically closest to the clock-in, then measured lateness/overtime against that one segment. Tested against this project's own live split-shift data (a real 3-segment shift, `09:00-10:00 / 11:00-18:00 / 20:00-22:30`), that heuristic silently caps lateness at half the gap between segments — arriving 61 minutes late for the 09:00 segment reads as "0 minutes late" because 61 minutes past 09:00 is nearer the 11:00 segment's start. It also badly over-counts overtime for the single most common real failure mode this redesign now explicitly targets (§3's new clock-out sweep): a session that spans an entire midday break because the employee forgot to clock out at lunch reads as ~9 hours of overtime, because "nearest start" matches it to the segment with the earliest end. The corrected computation instead sums each session's actual time-overlap against *every* segment it touches (`scheduled = Σ overlap(session, segment_i)`), and derives late/overtime minutes from `worked − scheduled` rather than a single boundary comparison — correctly handling a session that spans a gap, touches multiple segments, or partially overlaps one. Segments where `end < start` (crossing midnight) are rejected at shift-creation time with a plain-language message rather than silently producing nonsense minutes.

Computed fresh wherever displayed — never stored. Three consumers:

1. **Employee's own Attendance screen** (§5) — today's running total.
2. **Manager's live roster** (§7) — an OT chip appears on a row once someone crosses their grace period for the day.
3. **`POST /payroll/calculate` response** — `attendance_summary` gains `total_late_minutes` (cumulative across the period, not just `late_days`' existing count) and a new `overtime_minutes` field, both purely informational. `calculation.net_amount` is **not** affected — track-only, as confirmed. The owner sees the numbers and decides any bonus manually at disbursement, same as today's existing (already-built) bonus field.

## 7. Manager/owner: redesigned "Attendance & Payroll" hub

Adds a new hub screen for owner/manager — the employee/counter_staff/florist_staff/delivery_partner `AttendanceStack` experience is untouched (their own clock-in + "My Advances," as today). Two tabs on one screen:

- **Today**: live roster, one row per staff member, each showing exactly one primary contextual action (not a stack of icons, per `staff-ux-checklist` #2) — "Clock In" for someone who hasn't clocked in and hasn't finished for the day, "Clock Out" only for someone whose session is actually still open (not merely present in today's history — someone who finished hours ago gets no action, correcting an earlier draft that would have offered "Clock Out" to an already-departed employee and hit a plain 400). Status per row: **in / shift complete / not clocked in**, plus an OT chip once applicable (§6). A location filter (the old `StaffAttendanceScreen`'s chips, not dropped), the same four summary tiles that screen already has, and per-session expansion for a split-shift day's separate segments are carried over — the roster is a genuine superset of what `StaffAttendanceScreen` showed, not a smaller replacement for it (see the capability-preservation correction below). A pending-advance-requests count badge. Defaults to the manager's own assigned location (owner defaults to "All," matching the existing pattern already established in `OrdersInboxScreen.js`'s location filter) — with results de-duplicated per person (a staff member assigned to more than one location previously appeared once per assignment in the "not clocked in" list).
- **Manage**: Shifts, Salaries (owner-only — the existing gate is preserved exactly, not widened), Payroll, Advances, Reports, plus (per the correction below) **My Attendance**, **Outdoor Requests**, and **Live Map** — reached directly instead of nested inside Quick Links. **No existing capability is removed**, only regrouped (`staff-ux-checklist` #9).
- **Dashboard banner**: a small new line for managers/owner — *"3 staff not clocked in"* — one tap into Today. Answers the "employees forget, and managers need an easy way to fix it" ask directly at the point managers already look first each morning, rather than requiring them to remember Attendance exists.

**Capability-preservation, corrected during plan review.** The original draft of this section repointed owner/manager's only route to `AttendanceScreen` at the new hub outright. A careful read of that screen found three things live *only* there with no other entry point in the whole app: **outdoor-duty request approval/rejection** (the only UI anywhere that can approve one — an employee who requests outdoor duty with no manager able to approve it is stuck mid-request, permanently, with no error shown), **a manager's own clock-in/out** (managers are staff for attendance purposes — `POST /clock-in` only blocks `owner` — and would otherwise lose the ability to clock themselves in at all), and **Live Map** (the only context-free entry point into live delivery tracking). Confirmed directly (2026-09-16): the new hub keeps `AttendanceScreen` reachable under its own route rather than replacing it, and the Manage tab gains three rows — **My Attendance**, **Outdoor Requests**, **Live Map** — pointing at that same existing screen's relevant sections, so nothing an owner/manager could do before this ships becomes unreachable after.

**Geofence pings as a secondary, not a headline, signal**: `geofence_events` already logs every enter/exit (unchanged by this design). Tapping into an individual's row can show their last geofence ping time as supporting detail — useful for the genuine edge cases (a mis-fired auto-clock-in that was undone, or a location with no GPS coordinates configured, where there's no geofence signal at all and manual clock-in is the only path) — but it's not promoted to a primary roster status, since for anyone with working geofencing the normal case has no gap between "arrived" and "clocked in" to cross-check.

## 8. Clock-out recovery sweep (added 2026-09-16, per direct confirmation)

The live data is direct evidence of what actually goes wrong day to day: 6 attendance sessions in the dev DB are still open, one since June. The exit-timeout auto-clock-out (§1) depends on the employee's phone continuing to run a background task; a dead battery or a force-quit app means it never fires, and nothing else in the app today notices. A server-side sweep (extends the existing `server.js` cron alongside the geofence-timeout check it already runs) now scans for sessions still open more than N hours past their matched shift-segment end (using the same segment-matching this design already builds for §6), auto-closes them with a distinct `clock_out_method = 'auto_shift_end'`, and — unlike the geofence auto-clock-out, which needs no human decision — flags each one on the manager's roster (§7) for confirmation, since "closed automatically because the shift ended" is a guess about when they actually left, not a fact the way a geofence exit is.

## 9. Salary advances → expense/register linkage (added 2026-09-16, per direct confirmation)

§4's `expenses.employee_id` column was originally justified partly as closing the "advances and salary aren't connected to reporting" gap, but the original draft only ever wired *disbursement* (§ below) to write an expense — advance *approval*, where cash actually leaves the drawer, wrote nothing at all: no expense row, no register adjustment, no `hasOpenRegister` guard. That's the same "cash moves, register doesn't know" bug class already fixed elsewhere in this codebase (`POST /customers/:id/credits`, per `CLAUDE.md`'s register/checkout sweep). `PUT /attendance/salary-advance/:id/approve` now gets the identical treatment `POST /payroll/disburse` gets: register-guarded when the advance is paid in cash, and a linked `expenses` row (`category: 'salary'`, `employee_id` set) written at approval time — so an advance shows up in financial reports the moment it's actually paid out, not only implicitly, later, as a deduction line inside a future payroll disbursement.

## 10. Error handling

Per `staff-ux-checklist` #6, every new error surface is plain language, not technical:
- Undo on a mis-fired auto-clock-in: a single tap, no confirmation dialog (still low-stakes within its now-bounded 15-minute window — see §5's correction; past that window the option simply isn't offered, rather than needing a confirmation dialog to stay safe).
- Missed-clock-in report failing to send: "Couldn't send that — try again," never a raw error. Capped to once per person per day server-side, so a confused employee can't repeatedly notify every manager.
- The register-closed message a cash-mode salary disbursement or advance approval can hit is worded for what's actually happening — paying *out*, not taking a payment — distinct from the generic cash-payment wording other routes reuse.
- The ten `florist_staff` `authorize()`/role-list fixes (§2) remove existing silent-failure states entirely (previously: blank/missing data, no message at all) — after the fix there's nothing new to word, those calls simply succeed.

## 11. Testing / verification approach

- `node app/scripts/babel-check.js` on every touched/created frontend file (existing project convention).
- A standalone unit-style check for the new `computeShiftWork`-equivalent function (late-minutes, OT-minutes-with-grace, overlap-based segment-matching per §6's correction) against hand-built fixture cases: on-time single shift, split shift both segments on time, split shift second-segment "false late" (the exact bug #3 case), OT within grace (no flag), OT past grace (flagged, minus the 30 min), a session spanning an entire gap between two segments (the forgot-to-clock-out-at-lunch case), a clock-in exactly at the midpoint between two segments, and a rejected midnight-crossing segment. Fixtures must include at least one **timezone-naive timestamp string** (no explicit offset) matching what the sync DB layer actually returns, not only explicit-offset strings — an offset-only fixture set would hide a real parsing bug the way an earlier draft's test suite did.
- Extends the existing `verify-register-expenses.js`-style regression script (or a new sibling, matching that pattern) to confirm `payroll/disburse` and advance-approval each correctly write a linked `expenses` row and that it appears in `GET /api/expenses/summary`.
- Live manual trace, matching this project's standing verification convention: one full day simulated for a split-shift employee (both segments, one deliberately-late second-segment arrival, confirm it does *not* flag late post-fix), one manager using the new roster's one-tap clock-in for a "forgot" case, one full payroll-calculate → disburse cycle confirming the expense/report linkage and the new late/OT fields, one simulated forgotten clock-out confirming the new sweep closes and flags it, and confirmation that every capability listed in §7's capability-preservation correction is still reachable.

## 12. Rollout / migration safety

Per `db-migration-safety`: before any of §4's changes run against the production database — take a backup, confirm the `salary_advances` constraint's actual current state in production specifically (not inferred from dev, which is already known to differ), and test the constraint-widen, the new columns, and the lat/long precision widen against a copy of real production data rather than only the empty/synthetic dev DB. The precision widen additionally needs the owner to re-enter each real location's actual coordinates afterward — the migration changes the column's capacity, not the accuracy of values already stored. These are implementation-plan steps, tracked there, not performed as part of this design document.
